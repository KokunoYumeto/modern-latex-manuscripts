## 1. Common Goal

The Noether project is not a collection of isolated translation attempts. It is
a source-canon-grounded, cross-lane mathematical translation and interlanguage
support program.

The controlling goal is:

1. Find, record, and publish usable target-language mathematical source-canon
   witnesses for every relevant language or language cluster.
2. Keep exact provenance: source URL, local path, language evidence, topic
   tags, hash, byte count when available, license or access signal, and reuse
   boundary.
3. Prefer source-level TeX/LaTeX, arXiv/e-print/source archives, GitHub source
   repositories, CTAN-style source packages, and other source-level mathematical
   files.
4. When TeX/source files are unavailable, use official, academic, or community
   PDF/DOCX/HTML/text/bibliographic witnesses as fallback evidence and mark the
   missing source-package gap explicitly.
5. Once a lane has sufficient baseline witnesses for a language/topic row,
   begin draft, non-canonical translation support for that covered row.
6. Keep uncovered rows in source-acquisition or gap status until they have real
   witnesses.

Generated translations, model output, OCR guesses, bridge terms, glossary
drafts, and private memory do not count as source canon. Russian or Ukrainian
evidence does not authorize other Slavic target languages. One language in a
cluster does not silently authorize another language in that cluster.

The working definition of useful work is concrete output. A session has not
served the program merely because it woke, read files, summarized itself, or
reported a plan. It must leave behind source-canon rows, acquisition rows,
draft translation rows, terminology rows, interlinear/scaffold rows, or a
packageable coordination artifact.

The current practical target is two-track:

1. Source-canon acquisition and publication for every under-covered active
   language.
2. Draft, non-canonical translation/interlinear work for every covered
   language/topic scope.

Those tracks run at the same time. Source-canon-first means "do not translate
without source witnesses"; it does not mean "never translate while more sources
could still be found."

## 3. No Idle Lanes

Every lane must do useful work in the current turn. A lane should not stop after
orientation, status reporting, or saying what it plans to do. The minimum useful
turn is an artifact-producing turn.

For each active row, language, term, topic, or local queue item, classify it
into exactly one of these current buckets:

- `source_canon_insufficient`: the row lacks enough target-language source
  witnesses for draft work.
- `source_canon_sufficient_for_draft`: the row has enough target-language
  source baseline for draft/non-canonical translation support.
- `blocked_by_access_or_license`: the row has a possible source but no clear
  access, license, or reuse boundary.
- `blocked_by_language_scope`: the witness is in the wrong language, wrong
  sublanguage, wrong script, or only a related cluster language.
- `blocked_by_topic_scope`: the witness is mathematical but not relevant to the
  specific concept/register/topic being translated.
- `not_applicable_to_lane`: the row belongs to another lane and must be routed
  rather than locally transformed.

For `source_canon_insufficient` rows, the lane must produce concrete acquisition
work:

- witness search terms used;
- candidate URLs and local paths;
- source type;
- language evidence;
- topic tags;
- license/access signal;
- hash or retrieval metadata when available;
- blocker reason;
- next acquisition action.

For `source_canon_sufficient_for_draft` rows, the lane must produce concrete
draft support:

- target-language rendering candidates;
- term alternatives and register notes;
- source-context notes tied to witnesses;
- formula-neighboring usage notes;
- interlinear or semi-constructed interlanguage scaffolds where useful;
- uncertainty notes;
- explicit non-canonical/no-review boundary.

Do not wait for every row in the lane to be sufficient before working on the
covered rows. Do not wait for every language in a cluster. Do not keep source
acquisition as an endless holding pattern after a scoped baseline exists.

Idle-session correction rule:

- If a session has been doing nothing, it must first read the GitHub instruction
  bus listed above.
- Then it must choose the next artifact-producing path from its lane state.
- If it has sufficient source baseline, it must produce draft/non-canonical
  translation support.
- If it does not have sufficient source baseline, it must produce source
  acquisition/provenance/gap artifacts.
- If its lane is a constructed/interlanguage support lane, it must produce
  review-only scaffolds, slot tables, relation-function notes, or terminology
  governance artifacts tied to source witnesses.
- It must not wait for B3 or the coordinator to spoon-feed a second prompt.

## 4B. Translation And Interlinear Work Requirement

When a lane has sufficient source baseline for a scoped row, the next work is
not another general source-status note. It is draft work grounded in the source
baseline.

Required draft/non-canonical translation support includes:

- target-language renderings of the scoped mathematical text;
- alternatives where source usage varies by register, region, or school;
- source-context notes explaining which witness supports which usage;
- formula-neighboring usage notes, especially around definitions, theorem
  statements, proof transitions, and algebraic notation;
- terminology ledger rows for core algebraic structures, finiteness concepts,
  invariant theory, document logic, and edition metadata;
- semi-constructed interlinear or interlanguage scaffolds when they help compare
  structure across lanes.

Semi-constructed scaffolds are review aids, not final languages and not
canonical editions. They may include relation-function slots, morpheme or term
slot notes, register comparisons, bridge-language alternatives, and
translation-memory style alignments, but must keep source witnesses visible.

If a language lane is known to be capable of translation in its scope, it should
translate the covered rows. It should not keep reporting readiness without
output.

## 5. Lane-Specific Posture

Coordinator/interlanguage lanes must maintain the overall map, keep GitHub
instructions coherent, route blockers, and identify which rows are ready for
draft work versus still blocked by source canon.

CJK lanes must preserve script/codepoint/layout discipline. If enough CJK source
witnesses exist for a scoped row, produce draft support with exact script and
formula-neighboring notes. If not, produce source-acquisition/gap rows.

Arabic/Persianate/Tajik lanes must preserve language and script separation.
Arabic does not authorize Persian; Iranian Persian does not authorize Dari or
Tajik; Dari does not authorize Tajik. When a scoped row is supported, produce
draft renderings and right-to-left or script-specific notes. When unsupported,
produce exact gap rows.

Romance lanes must not merely report source availability. French and Spanish
rows with enough witnesses should produce draft renderings and source-context
notes. Rows without enough witnesses should produce acquisition rows.

Slavic lanes must maintain non-Russian/non-Ukrainian target-language evidence
separately. Russian and Ukrainian may be historical baselines but are not enough
for other Slavic languages. Covered target-language rows should receive draft
support; uncovered rows should remain acquisition gaps.

R2 Pan-Turkic, R3 Arabic/Persianate/linear algebra, R6 Indigenous/Creole/Sign,
R7 Malay/SEA/Pacific, R9 Africa/Horn/West, and OLP/relation-function support
lanes must stop treating their first pass as a terminal status report. Each lane
must output either source-canon acquisition work or draft/interlinear support
for covered rows in the same turn.

OLP and relation-function lanes must also preserve the constructed or
semi-constructed review-only boundary. Their job is to build useful scaffolds,
slot ledgers, return ledgers, and review packet structures tied to source
evidence. They must not imply that a constructed surface is adopted, reviewed,
or publication-ready.

Interlanguage authority lanes must keep the whole program coherent: compare
source witnesses across lanes, flag places where one lane is waiting on another,
and identify which rows can move to draft support without waiting for unrelated
languages.

Coordinator lanes must not merely narrate packages. They should route work:
which session has enough source baseline and should draft, which session lacks
source evidence and should acquire, which output is packageable, and which
claim must remain forbidden.

Access, Indigenous, creole, and sign-language lanes must be especially careful:
authority, ethics, community access, and source provenance are part of the
artifact. Draft support may be produced only for scoped rows with adequate
witnesses and must remain non-canonical, not community-approved, and not a claim
of accepted terminology.

## 6. Git And Publication Boundaries

Language lanes do not push Git. They produce artifacts in their own workspace
outputs. B3/package steward stages, commits, pushes, verifies PR alignment, and
packages coherent publication drift.

Rolling packages must not include:

- credentials;
- raw unverified source bodies;
- raw OCR dumps;
- active OCR scratch directories such as `_tmp_pages` or `tmp_pages`;
- runtime caches;
- `.traineddata`;
- zip primaries, unless a dedicated gated source-canon artifact explicitly owns
  that publication.

Dedicated source-canon artifacts may publish gated payloads when they have
license/access/provenance handling and safety scans. Rolling packages are not a
dump channel.

B3's specific role:

- read the GitHub instruction bus before acting;
- verify current local/upstream/remote/PR head alignment;
- leave unrelated untracked or lane-owned WIP untouched;
- package only clean drift through the established rolling package builder;
- gate packages for credentials, raw bodies, zip primaries, runtime caches,
  active OCR scratch, `.traineddata`, and path-scope safety;
- stage only intended package or instruction artifacts;
- commit, push, and verify PR head alignment when publication is requested or
  when the package lane is active;
- update durable run logs and heartbeat/frontier records when appropriate;
- broadcast GitHub-visible common instructions to sessions when the user asks
  for cross-session alignment.

B3 should not convert language-lane WIP into final claims. It publishes
evidence, draft support, gaps, and coordination records.

## 7. Non-Claim Boundary

Every artifact must preserve the correct boundary. Unless a separate qualified
review record exists, do not claim:

- native review;
- canonical approval;
- accepted terminology;
- gate promotion;
- bridge promotion;
- blanket license clearance;
- translation completion;
- community approval;
- publication-quality final translation.

The expected outputs are source-canon/provenance/gap/draft/non-canonical review
materials. That is useful work. It is not final approval.

## 8. Operational Test

Before ending a turn, each session should be able to answer:

1. What files did I read from the GitHub instruction bus?
2. Which active rows are source-canon sufficient?
3. Which active rows remain source-canon insufficient?
4. What concrete source witnesses or gaps did I record?
5. What draft translation/interlinear support did I create for covered rows?
6. Where did I save the artifact?
7. What should B3 package?
8. What claims did I explicitly avoid?

If a session cannot answer those questions with filenames and row counts, it
has not done enough work yet.

## 9. Immediate Active-Work Command For Every Session

Every session should treat this as its next operating command:

1. Read the GitHub instruction bus.
2. Read its own lane outputs and the latest package/coordinator records.
3. Build an active-row bucket table.
4. For insufficient rows, acquire or document source-canon witnesses.
5. For sufficient rows, produce draft/non-canonical translation support and
   interlinear/interlanguage scaffolds where useful.
6. Save concrete artifacts under the lane outputs directory.
7. Do not push from language lanes.
8. Do not stop with a status-only note.

The success condition is not "the model understood the instructions." The
success condition is that the next packageable lane outputs contain source
witnesses, gap rows, draft renderings, terminology/register notes, or
interlinear/scaffold artifacts that another session can use.
